Harness Agent Call Center
E-commerce (Telesale)

Agent nhớ khách qua nhiều cuộc gọi và kênh, không hỏi lại, không bịa giá, không tạo đơn khi khách chưa đồng ý

Sudo Code 2026 — Vòng 1 · số liệu: bước 15 giai đoạn 2 (22 kịch bản, 3 seed)

Bài toán

  • Khách gọi lại hôm sau: agent mới hỏi lại tên, nhu cầu, diện tích phòng… — khách bực, cuộc gọi dài, bỏ đơn
  • LLM tự tin báo sai giá/khuyến mãi; tạo đơn khi khách mới chỉ "hỏi thử"
  • Cùng một khách đi qua hotline, Zalo, Fanpage nhưng hệ thống coi là nhiều người
  • Số điện thoại, địa chỉ của khách không được lộ vào LLM, log, trace

Giải pháp trong một câu

LLM hiểu, code kiểm chứng. LLM gọi tool (catalog, kho, giá, CRM, bộ nhớ) qua MCP; mọi điều có hệ quả — số tiền, tạo đơn, chuyển máy — có chốt bằng code và dẫn chứng nguyên văn từ lời khách.
  • Call Brief trước khi nói: khách là ai, đã tư vấn gì, không được hỏi lại gì, giá/tồn kho hôm nay
  • Bộ nhớ 4 tầng có TTL, lịch sử phiên bản khi khách đổi ý
  • Order gate + guardrail chặn đơn sớm và số tiền không khớp tool

Một lượt xử lý

  • 1–2. Sửa lỗi ASR, đổi số nói bằng chữ, che PII; nhận diện khách theo SĐT/Zalo/FB, nối định danh
  • 3. Call Brief: must_not_ask, must_carry_over, câu mở đầu tiếp nối; code tra sẵn giá/kho/KM
  • 4. LLM function-calling (≤ 6 vòng); code sửa SKU, chèn ngày, chống gọi lặp tool ghi
  • 5–6. Order gate: checklist → đọc lại đơn → khách đồng ý rõ ràng mới tạo đơn · Guardrail: số tiền phải có trong kết quả tool
  • 7. Trace theo schema BTC; hết cuộc → episode + trích rào cản/ngân sách/giá đối thủ

MCP: vì sao, và vì sao không A2A

MCP
  • một nơi ghi duy nhất → không hai nơi cùng ghi một khách
  • quyền theo caller, mặc định từ chối
  • nhật ký tool theo phiên
Không A2A
  • một agent + tool đủ cho kịch bản M1
  • thêm agent ↔ agent chỉ thêm lượt gọi LLM và độ trễ
  • module chuyên biệt chỉ còn làm nhánh dự phòng khi mất LLM

An toàn

  • Order gate luôn bật: không tạo đơn khi khách chưa xác nhận bản đọc lại
  • Guardrail: số tiền/phí/tồn kho khớp tool; chặn "đã lên đơn" khi chưa có tool; chặn "em là nhân viên thật"
  • PII: SĐT/địa chỉ/CCCD thành token trước LLM và trace; API trả trace rút gọn
  • Trần chi phí cứng mọi lần chạy thật; timeout 20 s + thử lại khi API đứng
  • Nhánh dự phòng mất LLM: chưa biết sản phẩm thì hỏi lại, không chọn bừa

Cách đo

  • 22 kịch bản: 7 mẫu BTC + 15 kịch bản sinh (đa phiên, đa kênh, ca biên); 3 seed; mỗi seed một mẫu
  • Chấm bằng reference_eval.py của BTC, 5 chỉ số: TSR · RQR · CCR · HR giá/KM · độ trễ
  • Baseline: cùng model và tool, bộ nhớ mới mỗi cuộc
  • Kịch bản BTC cố định không trả lời được order gate → báo riêng; số chính là TSR tương tác (khách mô phỏng trả lời gate)
  • Model agent gpt-4o-mini, temperature 0 · chưa có LLM-judge, chưa điền tay file chấm 20 lượt

  • Đã sửa và đo lại: giá sản phẩm phụ tính nhầm, thiếu price_vnd/qty, câu chuyển máy, gate lấn câu trả lời giá
  • Đã sửa, chưa đo: nhánh dự phòng chọn bừa SKU, lượt API đứng 68–128 s
  • Còn mở: CCR thiếu một nửa; order.update gọi trước khi khách đồng ý; hỏi lại "mã đơn hàng"

Hạn chế và việc tiếp theo

  • Dataset: 31 cuộc / 22 kịch bản (ngưỡng ≥ 120); audio 4 file TTS (ngưỡng ≥ 40 cuộc / 1 giờ)
  • ASR: Gipformer WER ≈ 8 % — chỉ trên 4 file TTS sạch giọng Bắc; cần ≥ 20 file nhiều giọng
  • Độ trễ: TTFT ≤ 3 s chưa đạt; cần tối ưu token và số vòng LLM
  • Đánh giá: chưa LLM-judge 12 tiêu chí, chưa chấm tay 20 lượt, chưa thí nghiệm cắt bỏ từng thành phần
  • Hệ thống: order gate ở orchestrator (chưa ở mcp-crm); API một worker
  • Mã nguồn, dataset, báo cáo: thư mục submission/ · chạy demo: python scripts/run_demo.py
